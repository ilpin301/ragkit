# Quickstart — from a zip to a working RAG base

This folder is the **kit**: every script, the shared venv, the skills and the
base template. Bases live *outside* it, one folder each, holding nothing but
their own data.

```
F:\____IL_AI\
  RAG\          <- this kit  (scripts, .venv, skills, template)
  PCM_RAG\      <- a base    (IN\, lightrag\.env, lightrag\data\)
  MECH_RAG\     <- a base
```

## Move the kit to another machine

```powershell
.\pack.ps1                     # writes ..\RAG-kit-<date>.zip (no venv, no git, no keys)
```

On the target machine, unzip anywhere, then:

```powershell
cd <unzipped folder>
.\bootstrap.ps1                # builds the venv, installs the skills, checks docker
[Environment]::SetEnvironmentVariable('RAGKIT_HOME', $PWD.Path, 'User')
```

Then **restart every shell and every running Claude session** — `RAGKIT_HOME`
is read at process start.

`bootstrap.ps1` needs: Python 3.13.x on PATH, Docker Desktop, and Ollama with
`ollama pull bge-m3` and `OLLAMA_HOST=0.0.0.0:11434` set user-level. It
downloads torch 2.7.1+cu126 and the pinned requirements — allow 15–30 minutes
and a few GB.

## Create a base

```powershell
.\new_base.ps1 -Name MY_RAG -Start
```

That is the whole thing. It picks a free port, generates a fresh server API key
and a unique `COMPOSE_PROJECT_NAME`, lays out `IN\` and `lightrag\`, writes
`.env` and the compose file, and brings the container up.

The LLM provider key comes from `$env:ZAI_API_KEY`, or `-ApiKey <key>`, or
`-From <existing base>` (which also copies that base's bindings). Without any of
them the `.env` gets a placeholder and the script warns.

| Flag | What |
|---|---|
| `-Name` | base folder name — the only required argument |
| `-Path` | where to create it. Default: this kit's parent directory |
| `-Port` | host port. Default: first free port from 9621 not claimed by a sibling base |
| `-From` | seed `.env` from an existing base, keeping its keys and bindings |
| `-ApiKey` | LLM provider key |
| `-Start` | `docker compose up -d` and wait for `/health` |

A new base starts on `NanoVectorDBStorage`. If it will hold more than a few documents, set
`LIGHTRAG_VECTOR_STORAGE=QdrantVectorDBStorage` in its `lightrag\.env` before the first ingest —
that is the whole switch while the base is empty: `new_base.ps1` has already written the base's
own `QDRANT_PORT`/`QDRANT_URL`, and the compose file already ships the `qdrant` service. Switching
after documents exist means a migration — see `OPERATING.md`.

## Use it

1. Drop PDFs into `<BASE>\IN\`.
2. Run `/il-rag-ingest` in Claude, or directly:
   ```powershell
   .\ingest.ps1 -Root <BASE> -ListFile <utf8 list of pdf paths>
   ```
3. Ask questions with `/lightrag-query`, check state with `/lightrag-status`.

Read `OPERATING.md` before the first real ingest — it covers what to verify and
how to recover. `NEW_BASE.md` covers the manual base layout for the cases
`new_base.ps1` does not fit.

## What is deliberately not in the zip

- `.venv\` — a venv cannot be copied between machines; `pyvenv.cfg` and the
  console-script shims embed absolute interpreter paths. `bootstrap.ps1` rebuilds it.
- `machine.ps1` — per-machine facts (venv path, CUDA verdict, Drive root),
  regenerated by `bootstrap.ps1`.
- Any `.env` — API keys never travel in the archive. Pass them to
  `new_base.ps1` on the target machine.
